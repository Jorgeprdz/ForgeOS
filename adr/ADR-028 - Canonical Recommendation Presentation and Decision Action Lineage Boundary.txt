ADR-028 — Canonical Recommendation Presentation and Decision Action Lineage Boundary

Status: ACCEPTED FOR PHASE_017E_COMMERCIAL_PILOT_EVIDENCE_ACTIVATION
Program: FORGE_COMMERCIAL_LEVERAGE
Phase: PHASE_017E_COMMERCIAL_PILOT_EVIDENCE_ACTIVATION / 017E-R1
Base main: db5b63298c0ed9303b22fb47cce0d59a9f8c9062
Branch: feature/forge-commercial-pilot-evidence-017e

Context

ADR-027 established the durable recommendation → explicit human decision boundary and locked ACCEPTED != ACTED, explicit lineage, advisor isolation, append-only evidence and non-causal interpretation. Phase 017E correctly stopped because two observability primitives were still missing: there was no canonical durable fact that a governed recommendation was presented in an authenticated productive UI, and existing productive action writers did not retain an optional explicit reference to the human-decision event that preceded a real action.

This ADR ratifies exactly those two evidence semantics. It creates no new recommendation, action, outcome, identity, commercial metric or source-of-truth authority.

Decision 1 — FES remains the only durable event-evidence ledger.

RECOMMENDATION_PRESENTED is added to the existing canonical FES event taxonomy. No second analytics or impression ledger is created. FES records only the observation that an already-governed recommendation was successfully delivered into an authenticated advisor's active productive UI in an interactable state.

Decision 2 — PRESENTED is narrowly defined.

PRESENTED != GENERATED.
PRESENTED != EVALUATED.
PRESENTED != VIEWED.
PRESENTED != READ.
PRESENTED != ACCEPTED.

RECOMMENDATION_PRESENTED means the governed recommendation reached the authenticated advisor's active productive UI after successful composition/render completion so that the advisor could interact with it. It does not claim visual attention or cognition.

Decision 3 — Presentation evidence is SYSTEM_OBSERVED and non-blocking.

The event source is SYSTEM_OBSERVED. The recommendation remains owned by its existing originating authority. A presentation-evidence write or sync failure must not hide, mutate or invalidate the recommendation and must not fabricate a successful durable presentation. The UI may remain usable while evidence truth remains unavailable until the existing FES runtime can persist/sync it.

Decision 4 — Presentation identity is distinct recommendation identity, not impression count.

Canonical presentation idempotency is scoped to:

advisor identity
+ recommendation_reference
+ recommendation_version

for the same governed recommendation version.

A refresh, remount, pageshow or return to the module does not create a second canonical presentation item. A materially new recommendation version is eligible for a new presentation item. If no authoritative recommendation version exists, the canonical stable decision/recommendation reference is the version identity and the event must not invent a synthetic revision merely from a render timestamp.

Decision 5 — Presentation event preserves existing authoritative identity.

The canonical envelope/payload preserves, where already available from the governed recommendation projection:
- advisor identity;
- recommendation reference;
- recommendation version;
- source authority;
- source domain;
- recommendation subject type/reference;
- presented_at;
- presentation_surface.

Fields already owned by the FES envelope are not duplicated unnecessarily. Missing optional recommendation metadata remains null/unknown; it is not inferred from display text.

Decision 6 — Real action authority remains unchanged.

ADR-027 Decision 4 remains controlling. Navigation, opening a module, accepting a recommendation or clicking an action CTA is not an action event. Only the existing productive action authority may establish ACTED by writing its existing canonical action evidence.

Decision 7 — Existing action evidence may retain optional explicit human-decision lineage.

An existing action event may carry an optional `recommendation_decision_reference` containing the canonical `SALES_NBA_ADVISOR_RESPONSE.event_id` that legitimately preceded that real action. The field is lineage metadata only. It does not change event type, action ownership, action semantics, funnel movement or outcome truth.

No new action event type, action ledger or action owner is created.

Decision 8 — Lineage transport may be ephemeral; productive truth is not.

The Home recommendation/action path may carry bounded ephemeral context between productive UI surfaces. Ephemeral navigation state is not evidence and is not business authority. The lineage becomes productive evidence only when the existing action writer validates compatibility and persists the reference on the real action event.

Local storage is not authorized as a commercial source of truth.

Decision 9 — Eligibility and compatibility are strict.

Automatic recommendation-decision lineage attachment is eligible only for explicit ACCEPTED or MODIFIED decisions. DEFERRED and DISMISSED decisions do not automatically mark a later action as execution of that recommendation.

Before retaining lineage, the action boundary must establish:
- decision advisor == action advisor;
- decision timestamp <= action timestamp;
- decision recommendation identity matches the transported governed recommendation identity;
- recommendation subject/action subject compatibility is explicit;
- commercial identity compatibility exists where required by the action owner.

Cross-advisor, name-only, guessed-person, wrong-subject or temporal-only matching is forbidden. If compatibility cannot be established, the real action may still be written by its existing owner but without recommendation lineage. Reconciliation state is UNRESOLVED or TEMPORAL_ASSOCIATION_ONLY as applicable.

Decision 10 — Outcome ownership and causality remain unchanged.

017E does not copy recommendation lineage directly into outcomes unless an existing outcome authority already owns such metadata. Existing action→outcome reconciliation remains authoritative.

Allowed observation chain:
RECOMMENDATION
→ PRESENTED
→ HUMAN DECISION
→ EXPLICITLY LINKED REAL ACTION
→ EXISTING OUTCOME RELATIONSHIP

This chain supports `observed after`, `explicitly linked`, `subsequent action`, `subsequent outcome`, `associated with`, same-advisor comparison and pilot evidence language only.

It does not authorize causal attribution.

Decision 11 — No database migration is authorized.

The existing FES ledger and existing RECOMMENDATION subject support must be reused. `event_type` taxonomy changes occur in the canonical application contract only. No migration, schema change, RLS change, auth change, dependency, lockfile or workflow change is authorized by this ADR.

If implementation proves a database change is required, Phase 017E-R1 must stop before any migration is created or applied.

Decision 12 — Pilot denominators use canonical presentations.

`RECOMMENDATIONS_PRESENTED` counts distinct eligible canonical RECOMMENDATION_PRESENTED evidence items, not render calls, page loads, projection evaluations or recorded decisions.

Decision-derived rates must distinguish zero, unknown, unavailable and insufficient sample. TEMPORAL_ASSOCIATION_ONLY does not count as explicit recommendation execution.

Consequences

Positive:
- Forge can truthfully establish a recommendation presentation denominator without claiming a view;
- refreshes do not inflate the pilot denominator;
- a real existing action can retain explicit decision lineage without changing action ownership;
- ACCEPTED remains distinct from ACTED;
- commercial pilot measurement can exclude temporal guessing;
- no parallel authority or ledger is introduced.

Tradeoffs and limitations:
- a presentation write failure means presentation evidence is unavailable even if the recommendation remained visible;
- pre-017E historical presentations are not inferred or backfilled;
- actions without validated explicit lineage remain unresolved/temporal-only for the governed pilot;
- DEFERRED/DISMISSED decisions do not automatically qualify later actions as recommendation execution;
- explicit lineage and subsequent outcomes still do not prove causation.

Acceptance

Phase 017E may close this boundary only when tests prove:
- evaluated-but-not-presented does not emit RECOMMENDATION_PRESENTED;
- authenticated successful presentation emits one idempotent canonical item per advisor/recommendation/version;
- refresh/remount does not inflate presentation count;
- a new governed recommendation version may produce a new presentation item;
- advisor isolation and failure-honest presentation semantics;
- ACCEPT/MODIFY/DEFER/DISMISS non-regression;
- ACCEPTED != ACTED;
- navigation alone creates no action;
- a real existing action can persist valid explicit decision lineage;
- invalid/cross-advisor/wrong-identity/action-before-decision/temporal-only cases are not counted as explicit lineage;
- existing outcome authorities remain unchanged;
- pilot metrics use canonical presentation denominators and non-causal language;
- no database, migration, auth, RLS, dependency, lockfile or workflow change occurred.

Final boundary

PRESENTED
!= VIEWED
!= HUMAN DECISION
!= COMMERCIAL ACTION
!= COMMERCIAL OUTCOME
!= CAUSATION
