Decision

Forge Aura Light 2026 is the official and canonical visual design authority for
all new Forge redesign implementation.

The normative artifact is:

docs/05-foundation/design-system/Forge_Aura_Light_2026_Sistema_de_Diseno.pdf

Version: 1.0
SHA-256: 0dbda2ae17d80602c7943bf139015177dbeb340a5edd5d9a5983bd24d5b6672e

Canonical rule:

Las acciones flotan. La informacion se organiza. El color orienta.

All new visual redesign work MUST comply strictly with the PDF. Framework
defaults, legacy screenshots, prior mockups, recovery CSS, Material 3 styling,
module-specific palettes and individual implementation preference do not have
authority to contradict it.

Scope

This ADR governs the visual and interaction language of:

- cleanroom frontend work;
- Forge shell and navigation redesign;
- Home and Smart Widgets;
- Pipeline, Activity, Quotes, Cartera, Commissions, Forecast, Reports and
  Configuration redesign;
- mobile, tablet and desktop layouts;
- components, primitives, cards, lists, tables, dialogs, sheets and tooltips;
- color, typography, spacing, radii, shadows, gradients and motion;
- floating bars and contextual actions;
- iconography and 3D illustration boundaries;
- accessibility and visual acceptance criteria;
- document-preview surfaces where Forge identity is represented.

Mandatory Boundaries

- Only canonical semantic tokens may govern new redesign implementation.
- Color must communicate identity, state or priority; decorative isolated color
  is forbidden.
- Actions and controls may float; informational content remains stable and
  organized.
- Information hierarchy must answer what happened, what needs attention and
  what the user should do now.
- Cards must not be created for every datum.
- Gradients are restricted to the authorized set and usage rules.
- Base productive text may not fall below 14 px.
- Touch targets must be at least 44 x 44 px.
- States may not be communicated only through color.
- Loading, empty, error, disconnected and no-permission states must be explicit.
- Example or fixture metrics may not appear as real production truth.
- Responsive implementation must preserve hierarchy rather than compressing a
  desktop dashboard.
- Legacy visual imports, recovery CSS, ad hoc inline styles and ungoverned local
  values are forbidden in the cleanroom redesign.

Supersession

This ADR prospectively supersedes prior visual directions for new redesign work,
including ungoverned Material 3 styling, recovery CSS conventions, dark organic
visual language, isolated module palettes and ad hoc component variants.

It does not retrospectively rewrite ADR-019, ADR-020, ADR-021 or ADR-023. Their
historical decisions and functional, runtime, quote, product and recovery
boundaries remain preserved.

This ADR does not itself authorize code implementation, route mutation,
deployment, schema change, RLS change, data mutation or business-logic change.
A separately approved execution scope remains mandatory.

Authority Precedence

Article 0, the Constitution, canonical truth and authority ADRs, security and
accessibility requirements remain higher-order authority. Within the visual
redesign domain, this ADR and its referenced PDF prevail over mockups, prior
visual documents, old screenshots, framework defaults and local preference.

Required Work Gate

Every redesign task must declare:

AURA_LIGHT_AUTHORITY=docs/05-foundation/design-system/Forge_Aura_Light_2026_Sistema_de_Diseno.pdf
AURA_LIGHT_VERSION=1.0
AURA_LIGHT_COMPLIANCE=REQUIRED
LEGACY_VISUAL_IMPORTS=FORBIDDEN
LOCAL_UNGOVERNED_TOKENS=FORBIDDEN
VISUAL_ACCEPTANCE_AGAINST_CANONICAL_PDF=REQUIRED

If this declaration is absent, the task is blocked by ROBOCOP LOCK 001.

Validation

Visual PASS requires evidence of canonical token use, semantic color use,
component hierarchy, responsive hierarchy, keyboard and focus behavior, zoom,
reflow, reduced motion, honest data states, no legacy visual imports and visual
comparison against the canonical PDF.

Screenshots alone cannot prove interaction, accessibility, responsive behavior
or data truth.

Change Control

Version 1.0 is locked. Any amendment requires explicit human-owner approval,
Miranda approval, Board approval, a versioned replacement artifact, a new
checksum and an ADR amendment or superseding ADR. Silent replacement in place
is forbidden.
